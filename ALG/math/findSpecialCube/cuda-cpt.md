## 二、推荐的 Jetson CUDA + CPU 混合架构

CPU：搜索控制器

参数范围、任务分块、运行状态、断点续搜

CUDA Kernel 1：并行候选生成

并行遍历 u、v，生成原始勾股数，执行低成本筛选

CUDA Kernel 2：数学剪枝

边长上下界、奇偶约束、模平方剩余筛选、候选压缩

CPU 多线程：因数分解与精确验证

最终验证器

精确整数运算验证三个面对角线、空间对角线和本原性

这是一套建议的架构，而不是已经在 Jetson 上实测过的性能结果。

## 三、哪些计算值得放到 CUDA？

| 搜索阶段                           | 推荐执行位置     | 原因                              |
| ------------------------------ | ---------- | ------------------------------- |
| 遍历 u,vu,vu,v 参数                | CUDA       | 候选之间独立，适合并行                     |
| 计算 u2−v2u^2-v^2u2−v2、2uv2uv2uv | CUDA       | 使用 64 位整数即可覆盖当前参数生成阶段           |
| 奇偶性和模运算筛选                      | CUDA       | 运算简单，可快速淘汰候选                    |
| 候选结果压缩与批次管理                    | CUDA + CPU | 只传递筛选后的候选，避免传输大量无用数据            |
| 分解 y−xy-xy−x、y+xy+xy+x         | 初期放 CPU    | 现有实现采用不规则试除和动态因子列表，直接 GPU 化需要重写 |
| 因子对枚举、平方验证                     | CPU 优先     | 便于复用现有代码并保证整数精确性                |

## 四、利用奇偶性，在 GPU 上提前剪枝

这部分与你前面分析的“两奇数、一偶数”直接相关。

欧几里得公式生成原始勾股数：

x=u2−v2,y=2uv,m=u2+v2x=u^2-v^2,\quad y=2uv,\quad m=u^2+v^2x=u2−v2,y=2uv,m=u2+v2

其中 x,mx,mx,m 为奇数，yyy 为偶数。再设：

a=kx,b=kya=kx,\quad b=kya=kx,b=ky

对于本原完美长方体，可以在进入因数分解之前增加以下必要条件。

条件 A：kkk 为奇数

此时 a,ba,ba,b 一奇一偶，第三条棱 ccc 必须为偶数，且本原完美长方体的偶数棱应能被 4 整除。因此：

c≡0(mod4)c\equiv0\pmod4c≡0(mod4)

对应平方检测条件：

C++

```
if ((k & 1) && (c2 & 15))
    continue;
```

该检查放在计算出 `c2` 后才有意义。

条件 B：k mod 4=2k\bmod4=2kmod4=2

对本原完美长方体，这个分支可以排除，因为 a=kxa=kxa=kx 中有一条棱会是 2 mod 42\bmod42mod4 的偶数，不符合本原解的奇偶结构。

C++

```
if ((k & 3) == 2)
    continue;
```

这条规则只用于搜索本原解，不能用于穷尽所有非本原整数解。

条件 C：4∣k4\mid k4∣k

此时 a,ba,ba,b 都是 4 的倍数。在本原搜索中，第三条棱 ccc 必须为奇数，因此可在平方根检测之前先检查：

C++

```
if ((k & 3) == 0 && (c2 & 3) != 1)
    continue;
```

这里的 `c2` 必须已经计算出来，且仍需执行精确完全平方验证。

这些条件能减少无效候选，但它们不能单独解决万亿级参数枚举的问题。因此，部署 GPU 之前仍然需要进一步收紧 u,v,ku,v,ku,v,k 的合法范围。

## 五、针对 Jetson Orin Nano 的实施路径

按照你之前使用的 Jetson Orin Nano / JetPack 6.2 环境，建议先实现一个 CUDA 原型，不必一开始就重写整个搜索器。具体可以分三阶段：

第一阶段：建立 GPU 性能基准。 选择较小的 uuu 区间，把 CPU 版和 CUDA 版生成相同的原始勾股数集合，对比结果是否完全一致，并测量每秒处理的候选数量。

第二阶段：增加分层筛选。 在 GPU 端增加奇偶性、合法边长范围和平方剩余条件，利用紧凑候选数组把少量存活结果传回 CPU。此阶段的核心指标不是 GPU 利用率，而是每 10810^8108 个初始参数最终剩下多少个需要因数分解的候选。

第三阶段：优化真正的瓶颈。 若 Profile 显示因数分解占据绝大部分时间，再评估 Pollard–Rho 的 CPU 多线程实现与 CUDA 并行实现。不要在尚未缩小候选空间之前，就投入大量工作实现 GPU 大数因数分解。

## 结论

可以使用 Jetson CUDA，但需要把它定位为搜索加速器，而不是用 GPU 暴力枚举替代算法优化。

当前最优先的工作应是修正 `max_u` 和搜索边界，明确本原解与全部整数解的搜索目标，然后设计 CUDA 候选生成及筛选 Kernel。等到候选空间明显缩小，再将 CPU 因数分解、GPU 筛选与精确验证组合起来。

还需要明确一点：完美长方体的存在性问题在 TheoremDB 截至 2026 年 7 月 31 日的记录中仍然开放。GPU 搜索可以验证一个有限范围，但不能仅凭某个范围内没有找到解，就证明完美长方体不存在。
